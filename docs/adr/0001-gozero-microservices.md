# ADR-0001：采用 GoZero 微服务拆分，而不是单体

- 状态：已采纳
- 日期：2026-10

## 背景

项目目标里明确写了"微服务网盘系统"，但微服务本身不产生业务价值。
真正要回答的问题是：**在这个规模下，拆分能换来什么，又要付出什么**。

## 决策

按"数据属主"拆成三个 RPC 服务（user / file / storage）和三个 API 服务，
服务之间只通过 gRPC 交互，不共享数据库表。

## 理由

1. **边界必须可验证**。`storage` 管上传状态机，`file` 管元数据与权限，`user` 管身份与配额。
   一旦允许跨服务直连数据库，"边界"就只是一句注释。
2. **故障隔离**。对象存储抖动时，登录与列表接口不应受影响。
3. **学习目标**。项目本身要展示服务治理（服务发现、超时、熔断、指标），
   单体无法承载这些内容。

## 代价

- 一次上传要跨 3 个服务、5 次 RPC；
- 部署单元从 1 个变成 6 个（compose 里能直接感受到启动顺序的麻烦）；
- 跨服务一致性只能靠编排 + 补偿（见 ADR-0004）。

## 替代方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 单体 + 模块化 | 事务简单、部署简单 | 无法展示服务治理；故障不隔离 | 不满足项目目标 |
| 按业务拆 3 个服务（本方案） | 边界清晰、可独立扩展 | 一致性复杂 | **采纳** |
| 拆得更细（每张表一个服务） | "看起来更微服务" | 纯 CRUD 拆分，没有收益 | 过度设计 |

## 后果

- 必须为每个跨服务写操作设计幂等与补偿；
- 可观测性成为必需品而不是可选项（不然无法定位跨服务问题）。
