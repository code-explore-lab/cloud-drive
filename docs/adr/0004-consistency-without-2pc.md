# ADR-0004：跨资源一致性用编排 + 幂等 + 补偿，而不是分布式事务

- 状态：已采纳
- 日期：2026-10

## 背景

一次"上传完成"要改三处：MinIO 里的对象、`storage` 的对象元数据、`file` 的版本与 `user` 的配额。
MySQL 事务管不到 MinIO，也不该为了两个数据库引入 XA/2PC。

## 决策

1. **不做分布式事务**。用「顺序 + 幂等 + 补偿 + 对账」收敛。
2. **写入顺序：外部副作用在前，数据库状态在后**（先对象、后元数据）。
3. **删除顺序反过来：先数据库不可见，再删对象**。
4. **每个关键步骤都有幂等键**：`uploadId`、`request_id`、`idempotencyKey`。
5. **失败留痕 + 可重试**：`last_error`、`gc_attempts`、后台维护任务、Prometheus 指标。
6. **对账兜底**：`tools/reconcile` 找出"记录在但对象不在""对象在但无记录""配额与版本不符"。

## 理由

- 2PC 需要所有参与者支持事务协议，MinIO 不支持；引入它会把系统变成一堆无法独立演进的组件。
- 幂等 + 重试 + 对账 是**可解释**的：任何时刻都能说清"现在处于哪个状态、下一步谁来做"。
- 代价是存在短暂不一致窗口，但这些窗口都有明确的修复路径（见 `docs/consistency.md`）。

## 已知的不一致窗口

| 窗口 | 影响 | 兜底 |
| --- | --- | --- |
| 合并成功但 `storage_objects` 写入失败 | 孤儿对象 | 重试完成覆盖写；reconcile 列出孤儿 |
| 版本写入成功但配额提交失败 | 配额少扣 | reconcile 报告；后续可做自动修复 |
| 对象删除成功但状态更新失败 | 记录说可用、实际不存在 | 下载报错；reconcile 发现 |
| 目录递归删除中途失败 | 部分子项残留 | 重新删除（幂等） |

## 替代方案

| 方案 | 结论 |
| --- | --- |
| XA / 2PC | MinIO 不支持；运维复杂；否决 |
| 事件溯源 + 最终一致（Kafka） | 更彻底，但当前没有吞吐压力，属于 Phase 5 |
| 本方案 | 显式窗口 + 可观测 + 可修复，符合"先正确"原则 |

## 后果

- 必须在文档里如实写明这些窗口（不能假装原子）；
- 必须有对账工具与相关指标，否则窗口会变成"永远修不好的脏数据"。
