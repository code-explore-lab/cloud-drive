# ADR-0006：内容摘要"按需校验"，不做默认全量校验

- 状态：已采纳
- 日期：2026-10

## 背景

上传完成后，如何确认对象内容与客户端发送的内容一致？

- 方案 A：总是把合并后的对象完整读一遍，计算 SHA-256 与客户端声明比对；
- 方案 B：只在客户端显式提供 `contentHash` 时校验；
- 方案 C：完全不校验，靠 HTTPS 与分片长度。

## 决策

采用方案 B：

- 客户端在 `POST /v1/uploads` 里可选传 `contentHash`；
- 提供时，完成阶段流式读一遍对象并比对，不一致则删除对象、任务置 `failed`、返回 400；
- 不提供时跳过，`storage_objects.content_hash` 留空，`hash_verified=0`。

## 理由

1. **成本真实存在**：读一遍 10GiB 对象意味着 10GiB 的 MinIO 出口流量与 CPU（SHA-256）；
   把它变成默认行为会让"上传 1 秒、校验 3 秒"。
2. **分层校验已经覆盖大部分问题**：每个分片都有精确长度校验与 ETag，
   传输层的错误会先在这里暴露。
3. **可观测**：`hash_verified` 字段让"有多少上传真的校验过"变成可查询的事实，
   而不是靠猜。

## 代价

- 默认情况下无法发现"内容被篡改但长度一致"（例如恶意客户端）；
- 需要客户端配合才有完整保证。

## 替代方案

| 方案 | 结论 |
| --- | --- |
| 总是校验 | 安全但昂贵；适合金融/合规场景，不适合当前定位 |
| 从不校验 | 太弱，无法回答"内容一致吗" |
| 按需校验（本方案） | 在成本与保证之间取平衡，且把选择权交给调用方 |

## 后果

- API 文档必须明确写出"提供 contentHash 才会做整文件校验"；
- 端到端测试覆盖了"提供 hash 且内容一致 → 成功"与"分片长度不符 → 400"，
  摘要不匹配的路径由单元测试与手工验证覆盖。
